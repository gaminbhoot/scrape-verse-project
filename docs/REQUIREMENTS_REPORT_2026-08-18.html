0 What this hackathon is actually testing

Not “can you scrape”. Can you turn an unreliable long-tail site into a reliable, typed API that an agent drives — and that heals itself. Every track rewards platform advocacy.

Winning thesis
Pick a long-tail public site no one else touches (no prebuilt), build a custom Collector in Scraper Studio from a natural-language prompt, drive it via POST /dca/trigger from a coding agent in the terminal, deliberately break it and show heal → approve, then serve the structured JSON as a real product.
Litmus test: if you replace Bright Data with requests + proxy and nothing changes about your demo, you lose.

1 Mandatory platform stack — what judges will verify

The 6-step CLI is not a tutorial. It’s the rubric. Dashboard-only builds will be penalized for Grand Prize.

#CommandPurposeJudge verification signal
1npx -p @brightdata/cliEphemeral install — no globalRepo/demo shows npx invocation, Node ≥18
2bdata loginOAuth → tokenUnits after it succeed; CI uses env-injected token, not interactive
3bdata scraper create <URL> "<data you need>"NL → Collector c_*Critical artifact. Collector ID documented, prompt specificity judged. Vague = weak.
4bdata scraper run <COLLECTOR_ID> <URL>Run → structured JSONJSON evidence from terminal, not dashboard click
5bdata scraper heal <COLLECTOR_ID> "<what broke>"Self-heal on changeTheme compliance. Real breakage + heal with same ID. Skipping = fails theme.
6bdata scraper approve <COLLECTOR_ID> / --rejectHuman gate on heal diffShows review of proposed patch before merge

Collector lifecycle

create → c_*→run / POST /dca/trigger→heal (proposed)→approve → same c_*
  • Format c_* — permanent handle. Heal is mutative, not a new collector. Creating c_new to fix breakage = fails self-healing.
  • Trigger: POST /dca/trigger { collector_id: "c_xxx" } — REST with token from login. Async job → poll/webhook for delivery.
  • Scheduling: Bright Data native cron or your own (GH Actions, Vercel Cron, node-cron). One must be documented and running.
  • Store c_* in env (COLLECTOR_ID), never hardcoded, never logged.

Anti-patterns — why good pitches fail

  • “One-prompt + pretty dashboard” — 40 teams do it. Judges ask “why not prebuilt?” and “what happens tomorrow?” No answer = 6/10.
  • “Docs RAG without citations/incremental” — 2023. Need Sitemap diff, re-embed, source: url#anchor.
  • “10 sites in parallel — fast!” — Promise.all theater without judge metric. Needs coverage/schema/cost criteria + shipped winner.
  • “Agent writes Python scrapers” — Competing against Bright Data. Agent must output Studio prompt/collector, not Cheerio/XPath.
  • “Intel that summarizes without diffing” — Not sensing change. Store last-week snapshot, embed-diff, then summarize +3/-1 table.
Scope guard: Solo/duo → Hybrid A in 6 days (Discovery long-tail → trigger → S3 → GH cron → heal loop → diff/PR wall). That’s 80% of a win; rest is polish + heal video.

6 Self-healing — the hero demo

The entire point of Bright Data vs generic scraping. If you skip this, you compete as a generic scraper and lose Best Use regardless of product polish.

State machine (same c_*)

create→run ✓ JSON→site change → run ✗ 0/partial→heal “price selector .price → [data-testid=price]”→approve→run ✓ recovered
Downstream untouched: DB, dashboard, API consumers still hit same c_* via POST /dca/trigger. No re-wiring.
Heal semantics: bdata scraper heal <ID> "<what broke>" — description must be specific (“product price moved from .price to span.amount after redesign”), not “fix it”. Follow with approve (or --reject to discard). Judges check Heal is mutative.

60-second demo script (your crescendo)

  1. Agent: “find cheapest Y on [site]” → 5 rows.
  2. Change class / hide element (DevTools) or show pre-recorded site update.
  3. Re-run same prompt → heal log: selector .price-v1 not found → healed to [data-testid="price"]
  4. Data returns again. Show downstream DB/slack still flowing.

Failure modes & detection

BreakSymptomHeal handles?
Class rename0 records, 200 OK but empty✅ core case — AI locators
Structure / redesignFields wrong type, pagination broken✅ with schema re-inference
Anti-bot / CAPTCHA403/429, CAPTCHA HTML⚠️ platform unblocker, don’t heal on this — retry only
JS rendering shiftShell HTML, no data✅ browser rendering layer
Pagination changeCount drop >50%✅ Discovery re-discovers
Downtime 5xxTimeouts❌ never heal — backoff + alert
Detection triggers (before heal):
  • recordCount == 0 or completeness < 90%
  • Field null-rate spike (e.g., price null >30%)
  • Canary: known product must always be present
  • Schema validation via zod + rolling avg drop >50%
Guardrails: Require 2 consecutive 200+empty before heal. Max 3 heal attempts then alert. Validate healed selector matches ≥ expected nodes before persisting. Kill switch HEALING_ENABLED=false.

Automation ladder

LevelFlowJudge love
ManualDetect empty → human runs heal + approveBaseline — passes theme
Semi-autoDetector → propose heal → human gate → re-trigger → log diff to PRStrong
Full autoGH Actions cron fails → claude -p heals → auto-approve if confidence >0.9 → re-run → green checkWall of green

Downstream resilience — why same ID matters

  • Pipeline: POST /dca/trigger c_* → S3 versioned JSON → DuckDB — no code change on heal.
  • DB: Upsert by sku/url — re-run is idempotent, no dupes.
  • UI: “Healed at 14:03” badge proves liveness, not mock.
  • Alert: Slack “Healed selector X — no action needed” — proves recovering without breaking workflow.
Judges want: authenticity (real site change > artificial HTML edit), observability (structured logs with runId, oldSelector, newSelector, completenessBefore/After), rollback via previous config.
